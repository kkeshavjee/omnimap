1. Executive Summary
OmniMap is a web-based clinical terminology mapping platform developed by Omni Health Nexus Inc. (OHN). It provides a structured, auditable, statistically rigorous workflow for mapping source clinical codes and terms to any configured target terminology — including SNOMED CT, LOINC, ATC, CCDD, ICD-10/11, and custom code systems — and exporting results in FHIR-compliant and other standard formats.

OmniMap's core innovations are: (1) an EMR term sampling module that extracts, frequency-ranks, and stratifies source terms from uploaded data using Pareto and other sampling strategies, with intelligent management of long tail terms and net-new terms across successive extracts; (2) a dual-independent-review workflow with automated discrepancy escalation, a reviewer pool model, dynamic load balancing, and terminology affinity-based assignment; (3) a terminology-agnostic architecture supporting any source-to-target code system pairing; (4) a regex pattern library with AI-assisted generation trained on OHN's proprietary corpus, over-greedy detection, and conflict resolution; (5) a prospective validation holdout module with power-calculation-driven sample sizing for Precision, Recall, and F1 against a minimum threshold of 0.90; (6) a four-point validation scoring scheme (0–3) mapping directly to the confusion matrix; (7) an automation evaluation module for benchmarking AI/NLP matching tools; (8) a reviewer training and certification system with hard competency gates; and (9) a terminology version validation project type for managing drift across terminology releases.

OmniMap is built on a multi-agent orchestrator-worker architecture following current industry best practices, with human-on-the-loop design throughout. It does not itself constitute a regulated Software as a Medical Device (SaMD). All data is processed under agency agreements with data controllers; OHN acts as data processor only.

2. Background & Motivation
2.1 The Terminology Mapping Problem
Clinical data generated in healthcare settings is encoded using a heterogeneous mix of local, proprietary, and international code systems. Transforming this data into semantically interoperable assets requires systematic mapping between code systems. Target terminologies include SNOMED CT, LOINC, ATC, CCDD, ICD-10/11, and institutional code sets. This process is labour-intensive, error-prone, and typically lacks rigorous quality assurance. A further challenge is dataset scale: EMR term distributions follow a power law, with a small number of high-frequency terms accounting for the majority of clinical encounters, and a very long tail of low-frequency terms that are individually rare but collectively significant.

2.2 Evidence Base: Barriers to Jurisdictional Scalability
OHN's hands-on engagement with pan-Canadian EMR data (1.2 million de-identified patient records) and Snap2SNOMED-assisted mapping of the CPCSSN dataset, combined with a targeted review of peer-reviewed and gray literature, identified five structural barriers to jurisdiction-wide terminology adoption (Keshavjee & Guergachi, 2026):

Workflow misalignment: Coding work falls on clinicians during time-pressed clinical encounters, creating friction rather than value.
Insufficient localization: Standard terminologies lack Canadian synonyms, bilingual content, and curated value sets relevant to local practice.
Inadequate error surfacing: Developer-facing services provide weak exposure of inactivation reasons, historical associations, and version changes, allowing mapping errors and terminology drift to accumulate undetected.
Maturity model gaps: Existing implementation frameworks ignore complexity in early stages, causing technical debt to accumulate before basic mapping capability is achieved.
Lack of structural incentives: Costs and benefits of terminology adoption are misaligned across vendors, clinics, and jurisdictions.

OmniMap directly addresses barriers (1), (3), and (4) through workflow-embedded mapping, robust error surfacing and version drift detection, and a structured quality framework. Barriers (2) and (5) are addressed through the multi-terminology architecture and support for localized synonym sets and jurisdictional value sets.

2.3 Limitations of Existing Tools
Snap2SNOMED (CSIRO) represents the current state of the art but was not designed for multi-nomenclature use, reviewer pool management, or rigorous adjudication rate workflows. Additional limitations identified through operational use include: workflow rigidity with no dynamic term reallocation; no enforced reviewer independence; no formal discrepancy escalation mechanism; no regex generation or testing; no statistical power framework for validation; poor error correction ergonomics; and SNOMED CT-only support with no extensibility to other terminologies.

3. Product Vision & Objectives
3.1 Vision Statement
OmniMap will be the reference-standard platform for collaborative clinical terminology mapping — combining
statistically rigorous dual-review methodology, AI-assisted tooling grounded in human expert judgement,
and a power-user interface to produce auditable, FHIR-ready mapping artefacts at jurisdictional scale.

3.2 Strategic Objectives
Ingest EMR term data via file upload and support multiple sampling strategies including random, stratified, frequency-ranked, and Pareto-based 80/20 cutoff selection, with intelligent long tail and net-new term management.
Deliver a dual-independent-review workflow using a reviewer pool model with dynamic, affinity-aware allocation, automated discrepancy escalation, and terminology affinity tracking.
Support one-to-one and one-to-many mappings with structured confidence and equivalence scoring across any configured source-to-target code system pairing.
Provide a regex pattern library with AI-assisted generation trained on OHN's proprietary corpus, over-greedy detection, conflict resolution, and standalone export.
Enable prospective validation holdout with power-calculation-driven sample sizing against a configurable F1 threshold (default 0.90, one-sided alpha = 0.05).
Provide an automation evaluation module with four-point confusion matrix scoring (0–3) yielding Precision, Recall, and F1 from human-adjudicated gold standard labels.
Support terminology version validation as a distinct project type with automated change detection and inactivation reason surfacing.
Provide a reviewer training and certification system with hard competency gates per terminology domain.
Handle all source data under agency agreements with data controllers; OHN holds no data controller obligations.
Operate within OHN's ISO 13485-aligned QMS as a non-SaMD infrastructure component.

4. Users & Personas
4.1 Administrator
Manages the full mapping project lifecycle: uploads EMR extracts, configures sampling strategies, selects target terminologies, assembles reviewer pools, monitors cross-project progress, manages the regex corpus, and approves final outputs. Requires a high-level dashboard with real-time visibility across all active projects.

4.2 Reviewer (Expert Terminologist / Informaticist)
The primary power user. Certified per terminology domain before assignment. Receives an independently allocated subset of source terms and maps them without visibility into other reviewers' work. Uses a keyboard-driven, AI-assisted interface optimised for high-volume expert throughput. Can view their own performance metrics and competency profile as a personal efficiency tool.

4.3 Adjudicator
A senior expert who resolves discrepancies automatically escalated when two reviewers disagree. Sees both reviewers' choices in anonymised form, with full terminology hierarchy context and reviewer rationale comments. Adjudicator decisions are auto-accepted as canonical mappings. Must not have served as a reviewer on the same project.

4.4 Auditor
Read-only access to all project data, mapping decisions, reviewer statistics, and audit logs. Supports internal quality review, regulatory inspection readiness, and academic reporting. Cannot modify any records.

5. OmniMap Runtime DAG
OmniMap's orchestrator executes all project workflows as a universal directed acyclic graph (DAG) with conditional branches per project type. Each node has defined inputs, outputs, and transition conditions. The orchestrator is event-driven: each node completion triggers the next via AWS EventBridge / SQS. Nodes are implemented as discrete Lambda functions. This section defines the runtime behaviour of the application — the development build plan derived from this DAG is in CLAUDE.md.

5.9 Node 8 — CANONICALISE
Canonicalisation applies the OmniMap output convention to every confirmed mapping before it enters the corpus. This node receives input from two paths: (a) agreed or adjudicated reviewer mappings from Node 7, and (b) auto-matched terms from Node 4 that bypassed reviewer queues entirely. Both paths produce identical canonical output; the auto-accept flag distinguishes them in the audit log.

In:  Path A — Agreed or adjudicated mapping from Node 7
     Path B — Auto-matched term from Node 4 (source canonical = SNOMED CT FSN canonical)
Out: Canonical mapping record with the following conventions applied:
     • Auto-accept flag set for Path B entries. Audit log records match basis.
     • Source text: stored as original. Upper-case normalisation applied at match time only.
     • Replacement text: lower-case.
     • Replacement text wrapped in concept type XML closing tags:
         Diagnosis    →  <dx>term</dx>
         Medication   →  <med>term</med>
         Procedure    →  <proc>term</proc>
         Lab / Invest →  <lab>term</lab>
         Symptom      →  <sx>term</sx>
         Allergy      →  <allergy>term</allergy>
         Device       →  <device>term</device>
         Risk factor  →  <risk>term</risk>
     • Qualifiers in separate preceding tag: <qual>severe</qual><dx>diabetes</dx>
     • Audit log entry written (immutable, timestamped, user identity or system flag recorded)
Branch — project type:
     Standard mapping   → Node 9:  REGEX_PIPELINE
     Automation eval    → Node 12: SCORE
     Version validation → Node 13: DRIFT_REPORT

5.10 Node 9 — REGEX_PIPELINE
The regex pipeline executes as four sequential layers. Each layer operates on the output of the previous. Layers 1–3 use manually maintained corpora imported and versioned by the administrator. Layer 4 uses the OmniMap concept corpus grown by the review workflow.

LAYER 1 — UPPER-CASE NORMALISATION (not stored — applied at match time only)
  Source string converted to upper-case for all subsequent layers.
  Original string preserved in database. Normalisation is never persisted.

LAYER 2 — NEGATION REGEX (manually maintained corpus)
  Tags negation context: NO HISTORY OF → <neg>no history of</neg>
  Additive only — does not remove or reroute. Concept matching continues on full string.
  Example output: <neg>no history of</neg> DIABETES MELLITUS TYPE 2

LAYER 3 — QUALIFIER REGEX (manually maintained corpus)
  Tags qualifiers as separate preceding tags: SEVERE → <qual>severe</qual>
  Example output: <neg>no history of</neg> <qual>severe</qual> DIABETES MELLITUS TYPE 2

LAYER 4 — MANUFACTURER REGEX (manually maintained corpus)
  Strips manufacturer prefixes from drug names: APO-METFORMIN → METFORMIN
  Pure substitution — no tagging. Collapses brand/generic/prefix variants to canonical form.
  Enables concept regex to match METFORMIN once rather than all variants separately.

LAYER 5 — CONCEPT REGEX (OmniMap corpus — grows via review workflow)
  Maps upper-case terms to typed lower-case tagged replacement:
  METFORMIN → <med>metformin</med>
  Any remaining upper-case characters after substitution = incomplete match.

Final output example:
  <neg>no history of</neg> <qual>severe</qual> <med>metformin</med>

In:  Canonical mapping • concept cluster • four regex corpora
Out: Candidate regex pattern conforming to output convention
     Regex run report (see Section 5.11)
Triggers: Node 10 — REGEX_VALIDATE

5.11 Node 10 — REGEX_VALIDATE + POST-RUN REPORTING
Every regex pipeline execution produces a structured run report. Report items are routed to the reviewer interface or the administrator dashboard based on who needs to act.

6. Functional Requirements

6.1 EMR Term Ingestion & Sampling
Before mapping begins, OmniMap ingests source term data from uploaded EMR extracts and applies configurable sampling strategies to produce a working term set. The system manages de-duplication against prior mappings, handles net-new terms across successive uploads, and uses long tail terms to fill reviewer capacity above the power-determined minimum task load.

ID
Requirement
Priority
Notes
FR-01
Administrator uploads an EMR term extract as CSV or Excel. Required columns: source code, source display term, occurrence frequency count. Optional: clinical domain, source terminology identifier.
Must Have
Frequency count required for Pareto and frequency-based sampling. Terms without frequency can use random or stratified sampling only.
FR-02
On upload, system cross-references all terms against: (a) the completed mapping library, (b) all active project term pools, and (c) the regex corpus. Terms resolved by any of these sources are excluded from the working set and reported to the administrator as already-mapped.
Must Have
Prevents duplication of mapping effort across projects. Regex corpus matches are treated as pre-mapped.
FR-03
Net-new terms not present in any prior extract are identified and queued for the next project cycle. Administrator is shown a summary of net-new term volume and domain distribution.
Must Have
Net-new terms do not enter the current active project; they await the next Pareto analysis and power calculation.
FR-04
System displays the working term set as a frequency-sorted list with cumulative frequency percentage per row. List is sortable by frequency (descending default), cumulative percentage, and clinical domain.
Must Have
Enables administrator to visually identify the Pareto cutoff before sampling.
FR-05
Administrator selects a sampling strategy: (a) Random — simple random sample of N terms; (b) Stratified — random sample proportional to clinical domain; (c) Frequency-based — top N terms by occurrence; (d) Pareto — all terms up to an administrator-adjustable cumulative frequency threshold (default 80%). Strategies may be combined sequentially.
Must Have
e.g., Pareto first, then stratified within the Pareto set.
FR-06
Out-of-place terms (e.g., a procedure code appearing in a medication list) are flagged as data quality issues at ingestion and excluded from the working set. Administrator reviews and confirms exclusions before sampling proceeds.
Must Have
Out-of-place terms are a data quality issue, not a mapping decision. They are logged for upstream data quality reporting.
FR-07
Long tail terms (below the Pareto cutoff) are held in a prioritised queue. Priority score per term is computed from: (a) frequency trend across successive extracts (is this term growing?); (b) clinical domain risk flag (is it in a high-risk domain?). High-scoring terms are drawn first.
Must Have
Long tail queue persists across project cycles and is updated with each new extract upload.
FR-08
Minimum reviewer task load per project is determined by the power calculation (FR-17). Long tail terms are allocated to fill reviewer capacity above this minimum, drawn from the prioritised queue in order.
Must Have
Long tail allocation is automatic; administrator can review but not override individual term assignments.
FR-09
Administrator can view a sample summary before locking: total terms selected, % unique terms covered, % total occurrences covered, domain breakdown, and long tail terms allocated.
Must Have
Locking is required before reviewer assignment begins. Sample configuration is logged with timestamp.
FR-10
Administrator can regenerate the sample with different parameters before locking. All prior sample configurations are retained in the audit log. Regeneration is not permitted after reviewer assignment begins.
Must Have
ISO 13485 traceability requirement.

6.2 Prospective Validation Holdout
Before reviewer assignment begins, OmniMap draws a prospective holdout set from the sampled terms. This holdout is withheld from the main mapping workflow and later used as a gold-standard validation set to calculate Precision, Recall, and F1 against a minimum acceptable threshold. Sample size is determined by a one-sided statistical power analysis.

ID
Requirement
Priority
Notes
FR-11
Administrator configures validation holdout parameters before reviewer assignment. Default parameters: minimum acceptable F1 threshold = 0.90, power (1-beta) = 0.80, one-sided alpha = 0.05. All parameters are manually overridable per project.
Must Have
Hypothesis: H0: F1 <= threshold; H1: F1 > threshold. One-sided test is appropriate because the clinical and regulatory risk is asymmetric — an F1 below threshold has pipeline consequences; an F1 above threshold requires no action.
FR-12
System calculates required holdout sample size n using a one-sided power analysis framework for F1, based on the asymptotic variance of F1 (Goutte & Gaussier framework). Computed n is displayed to the administrator before confirmation.
Must Have
Power calculation method documented in system help text. Minimum n is enforced; administrator cannot reduce below the computed floor.
FR-13
System draws the holdout set using stratified random sampling from the full sampled term set, preserving clinical domain proportions. Holdout terms are removed from the main mapping pool and locked immediately.
Must Have
Holdout is drawn before any reviewer sees any term. No modifications permitted after locking.
FR-14
Administrator can view holdout set composition (size, domain breakdown, frequency coverage) but cannot view or modify individual term assignments until validation scoring is triggered after main project completion.
Must Have
Prevents selective exclusion of difficult terms.
FR-15
After main project completion, administrator triggers validation scoring. Holdout terms and their completed mappings are presented to two independent reviewers for gold-standard labelling using the four-point scoring scheme (FR-63 to FR-66).
Must Have
Holdout reviewers may differ from main project reviewers. Same blinded independence and adjudication workflow applies.
FR-16
System calculates Precision, Recall, F1, and 95% confidence intervals for each metric using gold-standard holdout labels. Results displayed in a Validation Report exportable as CSV and PDF.
Must Have
Precision = TP/(TP+FP); Recall = TP/(TP+FN); F1 = 2*P*R/(P+R). CIs: Wilson score for proportions; bootstrap for F1. Report includes pass/fail against the configured threshold.

6.4 Reviewer Pool, Assignment & Load Balancing
OmniMap uses a pool-based reviewer model. The administrator assigns a named pool of certified reviewers to each project. The system dynamically allocates terms from the pool, ensuring every term receives exactly two independent reviews, with allocation weighted by reviewer availability, throughput history, and terminology affinity.

ID
Requirement
Priority
Notes
FR-22
Administrator assigns a pool of two or more certified reviewers to each project. Only reviewers holding a valid certification for the project's target terminology may be included in the pool.
Must Have
Hard certification gate enforced at pool assembly. Uncertified reviewers are not selectable for a given terminology domain.
FR-23
Each reviewer sets their own availability per project (e.g., terms per day or hours per week). System uses availability as an input to allocation and load balancing. Reviewer can update availability at any time; load balancer rebalances remaining unstarted terms accordingly.
Must Have
Capacity control rests with the reviewer, not the administrator.
FR-24
System allocates terms such that every term is independently assigned to exactly two reviewers from the pool. Neither reviewer sees the other's assignment or response at any time. Independence is enforced at the data access layer, not merely the UI.
Must Have
Core quality control constraint. Cannot be overridden.
FR-25
Minimum task load per reviewer is determined by the project's power calculation (FR-12) divided across the pool, weighted by reviewer availability and affinity score. Long tail terms fill remaining capacity above this minimum (FR-08).
Must Have
Allocation is recomputed dynamically as availability changes.
FR-26
Load balancer automatically reassigns unstarted terms from lower-capacity reviewers to higher-capacity pool members when a reviewer's availability is exhausted. Reassignment is silent — no notification, no blame, no administrator intervention required. Independence constraint is maintained throughout.
Must Have
No-blame automatic reassignment. Administrator sees the reallocation in the dashboard but no alert is triggered.
FR-27
When a reviewer is assigned to multiple simultaneous projects, allocation across projects respects their per-project availability settings. System does not enforce cross-project capacity limits; the reviewer is responsible for setting realistic availability per project.
Must Have

6.9 Four-Point Validation Scoring Scheme
All validation activities in OmniMap — prospective holdout scoring and automation evaluation — use a four-point scheme that maps directly to the standard information retrieval confusion matrix, enabling unambiguous calculation of Precision, Recall, and F1.

ID
Requirement
Priority
Notes
FR-73
Score 0 — Correctly not coded (True Negative): the term has no appropriate target concept and was correctly left unmapped.
Must Have

FR-74
Score 1 — Correctly coded (True Positive): the term was mapped to the correct target concept.
Must Have

FR-75
Score 2 — Incorrectly coded (False Positive): a mapping was assigned, but no valid or correct target concept exists or was chosen.
Must Have

FR-76
Score 3 — Incorrectly not coded (False Negative): the term was left unmapped, but a valid target concept exists and should have been found.
Must Have

FR-77
Precision = TP / (TP + FP) = count(1) / (count(1) + count(2)). Recall = TP / (TP + FN) = count(1) / (count(1) + count(3)). F1 = 2 * Precision * Recall / (Precision + Recall). All calculated directly from four-point labels with no Partial category.
Must Have
Clean confusion matrix mapping. No partial match scoring.

7. Non-Functional Requirements
7.1 Performance
Terminology concept search must return ranked results within 500ms at the 95th percentile for any supported terminology, including SNOMED CT releases of up to 350,000 active concepts.
System must support concurrent sessions for up to 20 simultaneous reviewers across all active projects without performance degradation.
Page load time for the reviewer interface must not exceed 2 seconds on a standard broadband connection.
Regex corpus pattern testing against a 50,000-term EMR corpus must complete within 10 seconds.

7.2 Privacy & Security
All data in transit encrypted using TLS 1.2 or higher. All data at rest encrypted using AES-256 or equivalent.
Access is role-based (RBAC): Administrator, Reviewer, Adjudicator, Auditor. No cross-role data access is permitted at the application or database layer.
OHN processes source data as a data processor under agency agreements with data controllers. Privacy obligations — including breach notification under PHIPA, HIPAA, or other applicable legislation — rest with the data controller. OmniMap supports these obligations by maintaining complete audit logs and enabling timely incident reporting to the data controller upon request.
Source terms must be de-identified codes and display strings. OmniMap must not be used to process identifiable patient data without explicit data controller instruction documented in the applicable agency agreement.
All authentication must use multi-factor authentication (MFA) for Administrator and Adjudicator roles.

7.3 Auditability & Quality
Every state-changing action is written to an immutable, timestamped audit log with user identity (FR-19).
Audit logs retained for minimum 7 years and exportable as CSV.
System generates a quality report per project: total terms, adjudication rate, adjudication rate, unmappable rate, adjudicator override rate, and validation F1 score against threshold.

7.4 Reliability & Availability
Target uptime: 99.5% excluding scheduled maintenance windows.
Data backed up daily with point-in-time recovery capability.
System gracefully handles reviewer session interruption without loss of completed mappings. AI agent DAG sub-goal completion state is persisted for resumption from last successful node.

7.5 Regulatory Alignment
OmniMap operates as a non-SaMD infrastructure tool, developed under OHN's ISO 13485:2016-aligned Quality Management System (QM-01).
Software lifecycle documentation conforms to IEC 62304 Class B as a minimum.
Risk management per ISO 14971 for downstream risks from mapping errors propagating into OHN's SaMD outputs.

7.6 Data Persistence Requirements
The following constraints must be satisfied by the database design. Schema-level implementation is left to the development team.

Mapping records are immutable once written. Corrections create new versioned records; prior records are archived and flagged as superseded. No mapping record is ever deleted or overwritten.
Every state-changing action is written to an append-only audit log with user identity, action type, entity reference, and UTC timestamp. The audit log table must not support UPDATE or DELETE operations at the database layer.
Audit log records are retained for a minimum of 7 years and must be exportable as CSV without requiring application-layer access.
The regex corpus is versioned: each pattern record carries a version number, authorship (user ID or system agent identifier), creation timestamp, associated concept cluster ID, and validation status. Prior versions are retained on update.
Reviewer competency profiles and affinity scores are persisted across sessions and projects. Affinity scores are recalculated incrementally after each project completion and stored as snapshots with timestamps.
The prospective holdout set assignment is locked at draw time. The database must enforce that holdout term records cannot be modified after locking, and cannot be returned in reviewer assignment queries until validation scoring is triggered.
De-duplication cross-reference queries must perform efficiently across the full mapping library spanning all archived projects. Indexing strategy must support high-cardinality source code lookups within 100ms at 95th percentile.
Net-new term queue and long tail queue are persistent across sessions and project cycles. Queue priority scores are stored and recalculated on each new extract upload.
The database must support point-in-time recovery to any moment within the last 30 days, and full daily backups retained for 7 years.

8. System Architecture Overview
8.1 Architectural Principles
OmniMap is a cloud-hosted SaaS application built on a multi-agent orchestrator-worker architecture following current industry best practices (Anthropic Engineering, 2025; O'Reilly Radar, 2026). The core principle is hybrid control: a central orchestrator owns project state and workflow sequencing; specialized worker agents handle scoped sub-tasks with their own tools and failure boundaries. Human reviewers and adjudicators are explicitly positioned as the decision-making layer throughout — human-on-the-loop, not human-out-of-the-loop.

Task-Decoupled Planning (TDP) principles (Li et al., arXiv:2601.07577, 2026) are applied as a software construction methodology: each module is built with scoped context, local failure containment, and no cascading errors across module boundaries. This is an architectural construction principle, not a description of AI agent behaviour.

8.2 System Components
Orchestrator: Central workflow engine managing project state, reviewer pool allocation, load balancing, de-duplication, and sequencing across all modules. Single point of authority for workflow decisions. Delegates execution to specialized worker agents.
EMR Ingestion & Sampling Agent: Accepts CSV/Excel uploads, runs de-duplication against the mapping library and regex corpus, applies sampling strategies, manages the long tail queue, and draws the prospective validation holdout.
Reviewer Interface (SPA): Single-page application delivering the reviewer, administrator, and adjudicator interfaces. Reviewer interface optimised for keyboard-driven, low-latency expert use with split-screen layout, AI suggestions, and consistency tools.
Terminology Service: Pluggable multi-nomenclature adapter layer. For SNOMED CT: Snowstorm-based browser with ECL support. For LOINC, ATC, CCDD, ICD-10/11, and custom terminologies: code lookup, display term retrieval, and configurable relationship type sets. New adapters added without core platform changes.
AI Suggestion Agent: Generates ranked candidate target concept suggestions for each source term using semantic similarity ranking (NLP embeddings + confidence scoring). Suggestions are advisory; every suggestion requires explicit reviewer confirmation. Agent operates with scoped context per term — it does not receive full session history.
Regex Generation Agent: Generates candidate regex patterns for confirmed concept clusters, trained on OHN's proprietary regex corpus. Output is always reviewed and validated by a human before promotion to active status. Agent is retrained as validated patterns are contributed back to the corpus.
Discrepancy & Adjudication Engine: Compares reviewer pairs, detects disagreements, routes to adjudicator queue, and records auto-accepted adjudicator decisions.
Validation & Scoring Engine: Executes four-point confusion matrix scoring for prospective holdout and automation evaluation projects; calculates Precision, Recall, F1, and confidence intervals.
Terminology Version Diff Agent: Compares terminology release files or ingests change log APIs to detect inactivations, merges, definition changes, hierarchy changes, and new concepts. Surfaces inactivation reasons and historical associations.
Export Engine: Generates FHIR ConceptMap JSON/XML, regex JSON library, CSV, Excel, and PDF reports from canonical mapping records.
Database: Relational database for structured mapping data, audit logs, regex corpus, and competency profiles; search index for fast concept retrieval. See Section 6.6 for data persistence requirements.
Integration Layer (Phase 2): REST API endpoints and webhook support for OHN's EMR Data Cleansing Service and PARAT pipeline.

8.3 Key Design Decisions
AI is not trusted to map autonomously: AI suggestions and regex generation are inputs to human expert review, not outputs. Batch accept of AI suggestions is prohibited by design. This reflects the current state of AI/NLP reliability for clinical terminology mapping and the non-computability of lexical-to-semantic equivalence.
Independence is enforced at the data layer: reviewer blinding is not a UI convention — it is enforced by data access control. No reviewer can access another's responses through any interface.
No-blame automation: load rebalancing, dynamic reassignment, and quality flagging are all designed to be silent and non-punitive. The system acts; humans discuss.
Corpus as competitive moat: the regex corpus grows with every validated project, creating a self-reinforcing quality asset that improves AI generation over time. Corpus governance is an open strategic question as OmniMap scales.

12. Assumptions & Constraints
OHN maintains appropriate licensing for each target terminology: SNOMED International NRC membership for SNOMED CT; LOINC attribution (no fee); Health Canada and WHO licensing for CCDD and ATC respectively.
EMR term extracts uploaded for sampling contain occurrence frequency counts per term. Extracts without frequency data support random and stratified sampling only.
All source data is governed by agency agreements between OHN and the data controller. OHN holds no data controller obligations and is not responsible for breach notification.
Source terms are de-identified codes and display strings. OmniMap does not provide a de-identification step.
The prospective holdout set is drawn and locked before any reviewer sees any term. Holdout size is determined by power calculation and cannot be reduced after locking.
The adjudicator for a given project must not have served as a reviewer on that same project.
For Automation Evaluation projects, reviewers labelling automated output must not be the individuals who developed or tuned the automation system being evaluated.
Reviewer accounts are provisioned by OHN administrators. OmniMap does not provide self-registration.
FHIR ConceptMap exports are intended for OHN's internal FHIR infrastructure; OmniMap does not operate a FHIR server.

13. Success Metrics
Adjudication rate <= 20% on OHN's internal CPCSSN validation dataset within 90 days of Phase 1 deployment. Adjudication rate is diagnostic — it signals reviewer training gaps or terminology difficulty, not quality failure.
Auto-accept rate (identical SNOMED CT FSN matches) reported per project. Baseline to be established from first production project.
Mean time to complete mapping of a 500-term source set reduced >= 30% compared to Snap2SNOMED baseline (controlled comparison).
Validation F1 score >= 0.90 (one-sided, alpha = 0.05) on the prospective holdout set for OHN's first production mapping project.
Automation Evaluation Module produces consistent F1 scores (variance < 0.02) across repeated runs on the same gold-standard dataset.
Zero data-layer cross-role visibility incidents in penetration testing.
FHIR ConceptMap exports validated as conformant by the HL7 FHIR validator on 100% of test exports.
Reviewer interface usability: >= 90% task completion rate in usability testing with a cohort of 3 expert terminologists.
At least 3 target terminology adapters (SNOMED CT, LOINC, and one of ATC/CCDD/ICD-10) validated in Phase 1 with correct concept retrieval on a reference test set.
100% of reviewers assigned to live projects hold valid current certifications for their assigned terminology domains.
